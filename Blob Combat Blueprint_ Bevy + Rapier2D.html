Blob Combat Blueprint

Sekiro-style parry, dash and strike for a 2D Bevy + Rapier game. Design structure first, then language-agnostic pseudocode with sample values in section 12. Work through the sections in order; each one is a buildable milestone.

1The big picture: four layers, one direction

Data flows one way each tick. Nothing downstream ever writes back upstream. That is what keeps the feel deterministic and kills query conflicts like B0001.

  C --> D["4 Combat + Physics

  D --> E["5 Visual Rig

  D -. "events: Deflected, Hit, Struck" .-> C
LayerBevy scheduleOwnsNever does
Input + IntentPreUpdate / UpdateRaw input, double-tap detection, bufferDecide whether an action is legal
State machineFixedUpdateCurrent state, timers, cancel rulesTouch velocity or transforms
Combat + PhysicsFixedUpdate, before Rapier stepVelocities, parry arc test, hit resolutionChange state directly (emits events instead)
Visual rigUpdate (after interpolation)Blob deformation, arcs, particles, screen shakeAffect gameplay
Tight-feel rule: run all gameplay in a fixed timestep (e.g. 60 Hz) and measure every window in ticks, not seconds. Parry timing then plays identically at any frame rate.

4Parry resolution flow

The enemy never "asks permission." It emits a strike; one resolver system decides the outcome in a fixed priority order.

Check order matters: i-frames, then perfect parry, then guard hold, then hit. A dash that overlaps a parry window should always favor the player.

5Enemy tentacle handshake

Give every tentacle its own tiny state machine so the player can read it. The parry check only needs one question: "are you in ActiveStrike?"

stateDiagram-v2
  [*] --> Idle
  Idle --> Telegraph: attack chosen
  Telegraph --> ActiveStrike: telegraph timer done
  ActiveStrike --> Recover: strike finished
  ActiveStrike --> Deflected: parried
  Deflected --> Recover: recoil done, posture hit applied
  Recover --> Idle: recover done
  • Telegraph must be visually consistent (brighten, pull back, thicken). Players parry by rhythm, so vary timing between attacks, not the tell.
  • ActiveStrike exposes tip position and a few segment positions, nothing more. The parry system reads those.
  • Deflected is a free punish window for the player: extend the enemy's recovery here.

8Rapier2D setup

Use collision groups (Player, Enemy, PlayerAttack, EnemyAttack, Environment) so attacks never fight the blob's own body. Read collision events in the combat system and convert them into your own events; do not drive state straight from raw Rapier events.

Chain these explicitly with system sets. Split queries so no two systems in a chain borrow the same component mutably at once, and treat missing targets as a normal case: no player-facing panic when the lock-on query is empty.

10Game-feel checklist

MomentCue
Successful deflect2 to 4 tick hitstop, bright spark, tentacle recoils hard, small camera kick, crisp sound

Visual intensity should map to phase progress, so a late parry looks and sounds weaker than a perfect one. Players learn the window from that feedback.

11Suggested build order

  1. Neutral + lock-on strafe with the fixed-timestep loop and tuning resource.
  2. State machine skeleton with phase timers and debug text showing state and phase.
  3. Dash with i-frames; verify by drawing the i-frame window.
  4. One tentacle with Telegraph / ActiveStrike / Recover on a loop.
  5. Hit resolution and Staggered; enemy can now hurt you.
  6. Parry with arc test, deflect event, hitstop; tune the window here first.
  7. Attack with hitbox, combo buffer, posture damage.
  8. Input buffer and cancels, then the full visual rig and polish.
Debug tools to build early: draw the parry arc, i-frame window, active hitboxes and tentacle phase as gizmos, and add a slow-motion key. Tuning this kind of game without seeing the windows is guesswork.

12Pseudocode with sample values

This is Rust-flavoured pseudocode, not compilable. All values assume a 60 Hz fixed tick (1 tick is about 16.7 ms) and world units in pixels. Treat every number as a dial.

12.1 Tuning resource (one place for every number)

CombatTuning:
  tick_rate           = 60
  strafe_speed        = 260 px/s
  strafe_orbit_radius = keep current distance (no pull-in)

  dash:    iframe_ticks = 8,  glide_ticks = 8,  settle_ticks = 3
           speed = 520 px/s,  curve = ease_out,  cancel_after_progress = 0.70
  parry:   active_ticks = 8,  guard_ticks = 6,  recovery_ticks = 10
           arc_half_angle = 50 deg,  arc_range = 90 px,  move_scale = 0.30
  attack:  windup = 6,  active = 4,  recovery = 12
           lunge_speed = 180 px/s,  combo_max = 3,  posture_damage = 8
  stagger: ticks = 18,  knockback_speed = 400 px/s
  buffer:  max_age_ticks = 8,  double_tap_ticks = 12
  hitstop: on_deflect = 4,  on_player_hit = 7,  on_posture_break = 10
  posture: max = 100,  per_deflect = 12,  regen_delay = 90,  regen_per_sec = 20

12.2 Core data

enum PlayerState { Neutral, Dashing, Parrying, Attacking, Staggered }

enum Phase {                       // one flat list; each state uses a subset
  None,
  DashIframes, DashGlide, DashSettle,
  ParryActive, ParryGuard, ParryRecovery,
  AtkWindup, AtkActive, AtkRecovery,
  Stun
}

PhaseTimer { phase: Phase, elapsed: u32, total: u32 }
  progress() = elapsed / total          // 0.0 to 1.0, used by physics AND visuals

Intent { kind: Dash(dir) | Parry | Attack,  pressed_on_tick: u32 }

12.3 Input to intent (runs every frame, writes only the buffer)

fn read_input(keys, buffer, now_tick):
  strafe_axis = (D pressed) - (A pressed)       // continuous, not buffered

  for dir in [Inward(W), Outward(S)]:
    if just_pressed(dir):
      if now_tick - buffer.last_tap[dir] <= 12:    // double tap
        buffer.slot = Intent(Dash(dir), now_tick)
        buffer.last_tap[dir] = NEVER                // stop triple-tap re-fire
      else:
        buffer.last_tap[dir] = now_tick

  if just_pressed(PARRY):   buffer.slot = Intent(Parry,  now_tick)
  if just_pressed(ATTACK) and buffer.slot is not Parry:
                            buffer.slot = Intent(Attack, now_tick)

12.4 State machine (the only place that changes state)

fn can_accept(state, phase, progress, intent) -> bool:
  match state:
    Neutral   => true
    Dashing   => intent is Parry or Attack  and progress >= 0.70   // late cancel
    Parrying  => deflect_succeeded_this_parry                      // chain or counter
    Attacking => phase == AtkRecovery and intent is Attack
                 or phase == AtkRecovery and intent is Dash        // dash out of recovery
    Staggered => false

fn state_machine(tick):
  if hitstop.remaining > 0: return                // freeze all gameplay

  // 1. react to combat results (events written by the resolver, section 12.6)
  for ev in Hit events:
    if not has(Invulnerable) and state != Staggered:
      enter(Staggered, knockback = ev.direction * 400)
  for ev in Deflected events:
    deflect_succeeded_this_parry = true

  // 2. advance the timer
  timer.elapsed += 1
  if timer.elapsed >= timer.total:
    next = next_phase(state, phase)               // e.g. ParryActive -> ParryGuard
    if next exists: set_phase(next)
    else:           enter(Neutral)

  // 3. try to consume the buffered intent
  intent = buffer.slot
  if intent exists:
    if tick - intent.pressed_on_tick > 8: buffer.clear()          // too old
    elif can_accept(state, phase, timer.progress(), intent):
      enter(state_for(intent));  buffer.clear()

fn enter(new_state):
  state = new_state;  deflect_succeeded_this_parry = false
  set_phase(first_phase_of(new_state))
  match new_state:
    Dashing:  add Invulnerable (removed when phase leaves DashIframes)
    Attacking: clear hit_set                      // fresh "already hit" list per swing
  emit StateChanged(new_state)                    // visuals and audio listen to this

12.5 Velocity from state (writes Rapier velocity, nothing else)

fn apply_velocity(state, phase, timer, strafe_axis, to_enemy):
  tangent = perpendicular(to_enemy)               // orbit direction

  match state:
    Neutral:
      vel = tangent * strafe_axis * 260
    Dashing:
      t = timer.progress()
      speed = 520 * (1 - t)^2                     // ease-out: fast start, soft end
      vel = dash.direction * speed
    Parrying:
      vel = tangent * strafe_axis * 260 * 0.30
    Attacking:
      vel = to_enemy * 180 if phase in [AtkWindup, AtkActive] else 0
    Staggered:
      vel = knockback * (1 - timer.progress())    // decays over the stun

  body.linvel = vel
  body.angvel = shortest_turn(body.facing, to_enemy)   // except Attacking: facing locked
                  * turn_rate

12.6 Hit and parry resolver (one system, fixed priority)

fn resolve_strikes():
  for t in tentacles where t.state == ActiveStrike and not t.resolved:
    if not overlaps(t.tip, player.hurt_zone): continue
    t.resolved = true                             // each strike resolves exactly once

    if has(Invulnerable):                         // 1. dash i-frames
      continue

    if player.state == Parrying and phase == ParryActive:   // 2. perfect parry
      to_tip = t.tip - player.pos
      in_range = length(to_tip) <= 90
      in_arc   = angle_between(player.facing, to_tip) <= 50 deg
      if in_range and in_arc:
        emit Deflected { tentacle: t, point: t.tip }
        hitstop.remaining = max(hitstop.remaining, 4)
        t.state = Deflected;  t.recoil = -to_tip.normalized * 300
        enemy.posture += 12
        if enemy.posture >= 100: emit PostureBreak; hitstop.remaining = 10
        continue

    if player.state == Parrying and phase == ParryGuard:   // 3. soft block
      emit Hit { direction: ..., knockback_scale: 0.4, damage: 0 }
      continue

    emit Hit { direction: from t to player, knockback_scale: 1.0 }   // 4. full hit
    hitstop.remaining = max(hitstop.remaining, 7)

12.7 Tentacle tick

fn tentacle_tick(t):                               // skipped while hitstop > 0
  t.timer += 1
  match t.state:
    Idle:         if ai_wants_attack: t.state = Telegraph; t.timer = 0
    Telegraph:    if t.timer >= 24: t.state = ActiveStrike; t.resolved = false
                  // 24 ticks = 0.4 s readable wind-up; vary the gap BEFORE it, not the tell
    ActiveStrike: sweep tip along path;  if t.timer >= 10: t.state = Recover
    Deflected:    apply recoil impulse;  if t.timer >= 30: t.state = Recover
    Recover:      if t.timer >= 40 (or 60 if previously deflected): t.state = Idle

12.8 Hitstop

GAMEPLAY set run condition: hitstop.remaining == 0
  (state machine, timers, velocity, tentacle tick all skip)

fn hitstop_tick():                                  // always runs
  if hitstop.remaining > 0:
    if just_started: stash rapier velocities, set bodies to zero
    hitstop.remaining -= 1
    if now zero: restore stashed velocities

Visual set keeps running during hitstop: sparks, shake and squash animate
on real time, so the freeze looks crisp instead of dead.

12.9 Visual rig (reads state, never writes it)

fn blob_visuals(state, timer, velocity, to_enemy):
  p = timer.progress()
  match (state, phase):
    (Parrying, ParryActive):  arc_brightness = 1.0;  arc_width = lerp(60 deg, 40 deg, p)
    (Parrying, ParryGuard):   arc_brightness = 1.0 - p * 0.6   // fades out
    (Attacking, AtkWindup):   blob_stretch_back = ease_in(p) * 0.25
    (Attacking, AtkActive):   slash_ribbon_sweep = p;  ribbon_visible = true
    (Dashing, _):             stretch_along(velocity, amount = speed / 520 * 0.5)
                              spawn_afterimage_every(2 ticks)
    (Staggered, _):           wobble = sin(p * 40) * (1 - p) * 0.3
    (Neutral, _):             idle_breathing; core_offset = lerp(core_offset, to_enemy * 6, 0.2)

on Deflected event:  spawn_spark(point);  shake(amount = 4, ticks = 6)
on Hit event:        squash(direction);  vignette_pulse(0.4 s)
Pitfalls to avoid: (1) resolving the same strike every tick, so always set a resolved flag; (2) letting visuals or the resolver change PlayerState directly; (3) advancing timers during hitstop; (4) reading raw Rapier events as gameplay truth instead of converting them into your own events; (5) using unwrap on the lock-on query, since an empty query must mean "no target, stay Neutral."
Mapping to Bevy later: the CombatTuning and InputBuffer are resources, PlayerState and PhaseTimer are components on the player, the "emit" lines are events, and each fn becomes a system placed in the order from section 9.

14Building the player: Core + Mantle + Tendril

The plan is sound. The one change I’d make is to split the work by what each part needs to remember. The body only needs the current pose, so a shader is enough. The weapon needs history (for the slash trail), so it needs a mesh you rebuild each frame.

14.1 Technique choice per part

PartUseWhy
Mantle (blob body)One quad with a custom 2D material and an SDF metaball fragment shaderSmooth blending is free with a smooth-min, and deformation is just a few uniforms. A spring-ring mesh works too, but needs more CPU code for less visual gain.
Core (eye)A small separate glow circle, child of the visual rootIt must move independently of the body, so keep it out of the blob shader.
Tendril (weapon)One dynamic ribbon mesh, rebuilt every frameA trail needs past positions, which a stateless shader doesn’t have. One ribbon rig covers guard, parry and slash.
AfterimagesA small pool of fading ghost copiesCheaper and easier to tune than a history buffer inside the shader.

Never squash the physics entity. Stretch, shear and wobble go on VisualRoot only. The collider stays a clean circle, so a dash that looks like a long teardrop can’t change hit detection.

Two stages matter. First, targets: a system reads state and writes where each visual wants to be. Second, springs: a separate system moves the current visuals toward those targets. The springs are what make the blob feel alive, and this split keeps the state logic free of animation math.

spring_step(s, target, k, damping, dt):
  accel = k * (target - s.value) - damping * s.vel
  s.vel   += accel * dt
  s.value += s.vel * dt          // run in Update with real dt; visuals only

14.6 Tendril: one rig, three poses

The tendril is a ribbon sampled along a curve defined by 4 control points in the player’s local space. Each pose is just a different set of control points and a width and brightness. Blend the current points toward the target pose with a spring, then rebuild the ribbon.

PoseShapeSample values
GuardWide, soft arc around the frontHalf-angle 70 deg, radius 1.15 × body, alpha 0.5
Parry activeTaut, thin, bright crescent. Use the same numbers as the gameplay arcHalf-angle = tuning arc (50 deg), radius = tuning range, rim flash 1.0
Slash windupPulled back behind the start side25 deg past the start angle
Slash activeTip sweeps a cubic Bézier from one side to the other, flipping each combo hitSweep ±70 deg, t = ease_out(phase progress)
fn rebuild_tendril(rig, state, phase, p):
  target_pts = pose_for(state, phase, p)           // 4 control points
  rig.pts    = spring_toward(rig.pts, target_pts)  // smooth the morph

  // body of the ribbon
  for i in 0..24:
    t = i / 23
    pos    = bezier(rig.pts, t)
    normal = perpendicular(bezier_tangent(rig.pts, t))
    w      = rig.width * taper(t)                  // thin at both ends
    verts[2*i]   = pos + normal * w
    verts[2*i+1] = pos - normal * w
  write verts into the mesh (same vertex count every frame)

  // slash trail: remember where the tip WAS, in world space
  if phase == AtkActive: trail.push(world(tip))   // ring buffer of 12
  build second ribbon from trail; alpha = 1 - age/12 (dissolve)
Visual arc and gameplay arc must share numbers. If the crescent looks 60 deg wide but the check uses 50 deg, players will feel cheated. Draw the real arc as a debug gizmo over the crescent while tuning.

14.7 Making it in Bevy

  • Custom body shader: use a custom 2D material (Material2d) on a Mesh2d quad, with a fragment shader file. Pass lobe positions, colours and stretch as uniforms. Use a fixed-size array for the lobes.
  • Ribbon mesh: create the mesh once with a fixed vertex count and UVs (U along the ribbon, V across), then overwrite the vertex positions each frame. Use U for the dissolve fade in the shader.
  • Glow: bloom post-processing on an HDR camera gives the core and rim flash their glow. Check the docs for your Bevy version for the exact setup.
  • Smooth motion: physics runs in FixedUpdate, so draw the visuals from an interpolated position, or the blob will jitter against the camera.

Reference: the official shader material 2D example and the Material2d trait docs. Module paths for these types have moved between Bevy versions (some now live in bevy_sprite_render), so copy imports from the example that matches your version.

14.8 Visual build order

  1. Plain circle under VisualRoot, with the physics entity separate. Confirm it follows smoothly.
  2. Spring stretch and tilt on VisualRoot (dash teardrop, strafe lean, snap-back).
  3. Blob shader with satellite lobes replacing the circle.
  4. Core with offset toward the enemy, then state colours.
  5. Tendril guard pose, then the parry crescent tied to the tuning arc.
  6. Slash pose and Bézier sweep, then the trail and dissolve.
  7. Afterimages and hit wobble, then bloom and final polish.
Pitfalls: (1) scaling the collider with the visuals; (2) rebuilding the ribbon with a changing vertex count; (3) driving gameplay from visual positions; (4) stacking too many glowing effects, which hides the parry cue; (5) making the guard pose too busy, since the crescent snap only reads if the neutral shape is calm.
